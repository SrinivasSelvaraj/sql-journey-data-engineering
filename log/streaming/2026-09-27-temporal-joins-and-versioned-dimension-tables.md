# Temporal joins and versioned dimension tables

*Streaming and distributed processing*

## Concept

A temporal join connects fact events to the correct version of a dimension record based on time. Without it, you risk joining to the wrong dimension state: if a job title changes, a salary band shifts, or a remote-work policy updates, a late-arriving event might match against today's dimension instead of the one valid when the event occurred. This is especially critical in streaming where events arrive out of order and dimension tables evolve continuously.

In versioned dimension tables, each row carries validity timestamps (effective_date, end_date or valid_from, valid_to). When you join a fact event, you must filter the dimension to only rows where `fact.event_date BETWEEN dim.valid_from AND dim.valid_to`. Without this constraint, you get ambiguous or incorrect enrichment. For example, if a job posting from March references a job title that was renamed in April, a naive join without temporal filtering will pick up the new title, distorting historical analysis.

Streaming makes this harder because out-of-order facts arrive after their corresponding dimension versions have already been processed and potentially purged. You need either a complete SCD Type 2 history retained in storage, or a state store (like Kafka changelog topics or database-backed state in Flink/Spark Streaming) that can look up the exact dimension version at event time.

## Practice

**Problem:** You receive a stream of job_postings_fact events with job_posted_date. A separate dimension stream updates job_titles dimension with effective and end dates. A job posting from 2024-01-15 should always enrich with the job_title_short that was valid on 2024-01-15, even if the title changed to something else by 2024-03-01. Write a query that correctly joins the late-arriving fact to the versioned dimension.

```sql
SELECT
  jpf.job_id,
  jpf.job_posted_date,
  jpf.salary_year_avg,
  jpf.job_location,
  jtd.job_title_short,
  jtd.effective_date,
  jtd.end_date
FROM job_postings_fact jpf
INNER JOIN job_titles_dimension jtd
  ON jpf.job_id = jtd.job_id
  AND jpf.job_posted_date >= jtd.effective_date
  AND jpf.job_posted_date < COALESCE(jtd.end_date, '9999-12-31')
WHERE jpf.job_posted_date >= '2024-01-01'
ORDER BY jpf.job_posted_date, jtd.effective_date;
```

The key is the temporal predicate in the ON clause: the fact date must fall within the dimension row's validity window.

## Notes

- **SCD Type 2 is mandatory:** Without explicit versioning (start/end dates), you cannot perform temporal joins at scale. Never overwrite dimension rows; always insert new versions.
- **State store latency:** In Kafka Streams or Flink, the dimension changelog must be fully consumed before facts arrive, or you risk joining against stale state. Use interactive queries or external store lookups cautiously.
- **Handles out-of-order gracefully:** Once the dimension history is complete, temporal joins work correctly regardless of fact arrival order—the event timestamp, not processing time, drives the join.
- **Watch for clock skew:** If fact timestamps and dimension effective_dates are generated by different systems, clock drift causes silent mismatches. Validate timestamp consistency upstream.
- **Related: point-in-time joins, slowly changing dimensions (SCD), event time vs. processing time, windowed aggregations over versioned data.** Temporal joins are the bridge between streaming event enrichment and dimensional modeling.
