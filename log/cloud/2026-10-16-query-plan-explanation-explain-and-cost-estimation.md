# Query plan explanation: EXPLAIN and cost estimation

*Cloud platforms and storage*

## Concept

An execution plan (generated by `EXPLAIN` or `EXPLAIN ANALYZE`) shows *how* a database engine will execute your query—which tables it scans, what indexes it uses, whether it performs joins via nested loops or hash joins, and estimated row counts at each step. Cost is typically measured in arbitrary units (disk I/O, CPU cycles) but directly correlates to wall-clock time and cloud billing. Without understanding the plan, you're flying blind: a query might be slow because it's scanning 100M rows when an index could trim that to 1K, or because a join is executing in O(n²) instead of O(n log n).

Cost estimation is the engine's *prediction* of resource consumption before execution. It's based on table statistics (row counts, column distributions), index availability, and the optimizer's internal models. The estimate determines which query plan the optimizer chooses; if statistics are stale or missing, the optimizer may pick a terrible plan. In cloud environments (BigQuery, Redshift, Snowflake), understanding cost means understanding bytes scanned or compute slots consumed—directly impacting your bill.

Reading a plan teaches you about data flow: full table scans vs. index seeks, predicate pushdown, partition pruning, and memory requirements. This skill is foundational for tuning and for making architectural decisions (e.g., "do we need this index?" or "is our partitioning strategy working?").

## Practice

**Problem:** You notice that a query joining `job_postings_fact` with itself to find duplicate job postings is slow and expensive. Write an `EXPLAIN` query to diagnose whether an index on `job_title_short` and `job_posted_date` would help.

```sql
EXPLAIN ANALYZE
SELECT 
  a.job_id,
  b.job_id AS duplicate_job_id,
  a.job_title_short,
  a.job_posted_date
FROM job_postings_fact a
INNER JOIN job_postings_fact b
  ON a.job_title_short = b.job_title_short
  AND a.job_posted_date = b.job_posted_date
  AND a.job_id < b.job_id
WHERE a.job_work_from_home = true
  AND a.salary_year_avg > 100000;
```

**Expected output:** The plan will show estimated vs. actual rows at each step. Look for:
- Whether the `WHERE` clause filters before the join (good: fewer rows to join)
- Join type (hash join is typically better for large result sets than nested loop)
- Whether the index on `(job_title_short, job_posted_date)` is used in the join condition
- If the planner underestimated rows, stale statistics are likely culprit

## Notes

- **Stale statistics kill plans:** After bulk inserts, always `ANALYZE` (PostgreSQL) or refresh stats (Snowflake, BigQuery) so the optimizer has current row counts and distribution info.
- **Estimated vs. actual gap is a red flag:** Large differences mean the optimizer made wrong assumptions; investigate missing indexes, skewed data, or outdated stats.
- **Cost units vary by platform:** BigQuery counts *bytes scanned*; Redshift uses abstract cost; Snowflake counts *compute credits*. Always check the docs for your platform's billing model.
- **Predicate pushdown matters:** Filters applied *before* joins and scans reduce data volume dramatically. Check that your WHERE clause is pushing down past joins, not applied after.
- **Revisit after schema changes:** Adding indexes, changing partition keys, or denormalizing for performance will alter plans. Re-run `EXPLAIN` to verify the new plan is better.
